## 0. 为什么先有这份文档

静态演示站可以很快搭页面，但若**主基调与产品模型未对齐**，容易出现：

- 首页卖「画流程图」，实际产品是「项目 Dashboard + 角色配置」
- 排程被理解成调度引擎，而你的设计是**项目主脑的产出物 + 给人看的视图**
- 忽略「人必须确认产出」这条产品伦理，演示像全自动黑盒

**第一优先级**：在本文件定主模型与主界面叙事，再改工程和页面。

## 1. 产品模型（核心 · 已对齐）

### 1.1 一句话（对外）

> **Agent Flow：个人项目里的 AI 角色协作台——配置角色与工作流，在 Dashboard 上看阶段、排程与交付；关键产出经你确认后再进入下一步。**

### 1.2 十秒版

「配置 AI 角色，用工作流协作；Dashboard 看排程与交付，重要结果你来确认。」

### 1.3 三十秒版（路演）

1. **痛点**：一个人用多个 AI 角色做项目时，prompt 零散、交接混乱、进度靠脑子记。  
2. **方案**：在项目里**配置角色**（prompt、知识、交付规范），用**工作流**定义协作；内置**项目主脑**与人对齐后产出**排程**。  
3. **掌控**：**所有角色的产出都需人一定程度确认**——不是全自动黑盒。  
4. **边界**：当前对外为**高保真静态演示**；深度能力以交流为准。

### 1.4 概念分层

```text
项目 Project（容器）
├── 协作底座：文档、数据/资料仓库 …（与常见项目平台同类，演示可轻量呈现）
├── 角色 Roles（一等公民 · 可编辑配置包）
│     ├── 共用 Prompt / 行为设定
│     ├── 工作知识（文档或指针引用，不必复制全文）
│     ├── 交付契约：交给谁、命名规范、格式约定
│     └── 角色内规范（做事标准）
├── 工作流 Workflow（核心 · 真的怎么跑）
│     └── 角色之间的步骤、触发、产物传递
├── 项目主脑（内置角色 · 特殊）
│     └── 产出物 = 项目排程（与人沟通对齐后整理，需人确认后生效展示）
└── Dashboard（主界面 · 给人看的驾驶舱）
      ├── 项目阶段（方块）
      ├── 排程表（大 · 来自已确认的项目主脑产出）
      └── 角色卡片（最近交付 + 可选下一步/预计）
```

**关键原则（写文案时不可违背）**：

| 原则 | 含义 |
|------|------|
| **工作流是引擎** | 执行顺序、交接、触发以工作流为准 |
| **排程是视图** | 大排程表 primarily 给人看；内容来自**项目主脑**整理后的产出，且经**人确认** |
| **人确认产出** | 所有角色交付物都需用户一定程度确认后，才视为正式结果并驱动下游 |
| **角色 > 画布** | 差异化在「岗位配置 + 交付纪律」，不是单纯连节点 |

### 1.5 内置角色：项目主脑（项目主控）

每个项目内置 **项目主脑**（名称可在 UI 中统一，如「项目主脑 / 项目主控」）：

| 项 | 说明 |
|----|------|
| **职责** | 与人沟通项目目标与约束，整理并维护**项目排程** |
| **产出物** | **排程表**（Dashboard 右侧大表的数据来源） |
| **过程** | 主脑提出排程草案 → **与用户沟通确认** → 用户确认后写入「当前排程」 |
| **与工作流** | 排程**不替代**工作流执行；工作流定义「怎么协作」，排程回答「人何时该看到什么」 |
| **演示** | 可 mock「待确认排程」状态（如角标 / 确认按钮） |

### 1.6 人确认机制（全局）

所有角色（含项目主脑）的产出，产品设计上均经过 **Confirm / 确认** 环节：

- **默认叙事**：AI 起草 → 人审阅 → 确认 → 进入交付记录 / 传给下一角色 / 更新 Dashboard  
- **演示最低配**：至少 1 次「确认排程」+ 1 次「确认某角色交付物」的拟真交互  
- **话术**：强调「AI 协作，人做把关」，避免「全自动替代你」

## 2. 主用户与范围

### 2.1 主用户（已决）

| 项 | 决议 |
|----|------|
| **切入视角** | **个人**——一个人管理自己的项目与 AI 角色小队 |
| **团队** | 概念预留，**近期叙事不主打**；演示默认单用户单项目 |
| **能力语气** | 「可深度配置角色与工作流」，而非仅「零代码拖拽」 |

### 2.2 首要受众（演示对谁讲）

| 优先级 | 谁 | 关心什么 | 演示突出 |
|--------|-----|----------|----------|
| P0 | 个人 power user、独立 PM、创作者 | 一人控多角色、进度可见、产出可控 | Dashboard、角色卡片、确认流 |
| P1 | 小团队负责人（远期） | 统一协作方式 | 路线图提及即可 |
| 非首要 | 纯开发者 | API / 模型 | 被动回答 |

### 2.3 核心问题与价值

**问题**：多 Agent 协作缺少「项目感」——无阶段、无排程视图、无交付记录、无人把关。  

**价值**：

| 价值 | 用户语言 | 演示中如何看见 |
|------|----------|----------------|
| 角色资产化 | 像维护岗位说明书一样维护 Agent | 角色详情页（prompt、规范、交付契约） |
| 工作流协作 | 角色之间按契约执行 | 工作流 Tab / 编辑入口 |
| 可感知进度 | Dashboard 阶段 + 排程 + 卡片 | 主界面三区域 |
| 人确认 | 重要结果我说了算 | 确认排程 / 确认交付 mock |

## 3. 主界面：Dashboard（已决）

### 3.1 布局

```
┌─────────────────────────────────────────────────────────┐
│  [ Tab: 概览 ] [ 工作流 ] [ 文档 ] [ 资料库 ] …  ← 标签切换  │
├──────────────┬──────────────────────────────────────────┤
│              │                                          │
│  项目阶段     │           项目排程表（大）                  │
│  （方块）     │     （已确认的项目主脑产出 · 给人看）          │
│              │                                          │
├──────────────┴──────────────────────────────────────────┤
│  角色卡片 × N                                            │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐                    │
│  │ 项目主脑 │ │ 分析师   │ │ …       │                    │
│  │ 最近交付 │ │ 最近交付 │ │         │                    │
│  │ 下一步   │ │ 预计     │ │         │                    │
│  └─────────┘ └─────────┘ └─────────┘                    │
└─────────────────────────────────────────────────────────┘
```

### 3.2 各区域职责

| 区域 | 回答的问题 | 内容与规则 |
|------|------------|------------|
| **项目阶段（左上方块）** | 项目现在在什么阶段？ | 阶段名 + 简短状态；与工作流阶段/里程碑概念对齐，UI 独立成「状态牌」 |
| **排程表（右侧大图）** | 什么时候该有什么安排？ | 展示**已确认**的排程；待确认草案用明显状态区分；**只读为主**，改排程走「项目主脑 → 确认」 |
| **角色卡片（下方列表）** | 每个角色最近交出了什么？ | **强调已确认的结果**；可附「下一步 / 预计时间」；点击进角色详情 |

### 3.3 标签导航（已决）

顶部（或一级）**标签**切换主工作区，至少包含：

| Tab | 作用 |
|-----|------|
| **概览** | Dashboard（默认 landing） |
| **工作流** | 进入编辑/查看协作流程（**核心引擎**，点标签即可改） |
| **文档** | 项目文档（演示可静态列表） |
| **资料库** | 数据/资料仓库（演示可静态） |

原则：**工作流不必占 Dashboard 最大面积，但必须是一键可达的标签**——「有个标签能点进去修改」。

### 3.4 角色卡片字段（建议）

每张卡片最小集：

- 角色名 + 一行职责  
- **最近交付物**（已确认 · 带命名规范示例更佳）  
- **最近交付时间**  
- 可选：**下一步** 或 **预计交付**（弱化于「结果」，作补充）  
- 状态角标：`待确认` / `已确认`（有 pending 产出时）

**项目主脑卡片**：最近交付可展示「排程 v3 · 已确认」等。

## 4. 产品主基调

### 4.1 关键词

| 维度 | 方向 | 避免 |
|------|------|------|
| **身份** | 个人项目里的 AI 角色协作台 | 纯聊天工具、纯画流程图工具 |
| **用户感受** | 我在带一支可配置的 AI 小队，**我做最终确认** | 黑盒全自动、AI 替我做主 |
| **排程** | 主脑与人对齐后的「共识视图」 | 日历驱动引擎、改日期即改执行 |
| **技术露出** | 终端/状态/交付命名增强可信 | 堆砌模型名 |

### 4.2 内部共识一句话

> **Agent Flow = 项目化的、角色驱动的、人确认的多 Agent 工作流；Dashboard 是驾驶舱，工作流是引擎，排程是主脑与人对齐后的视图。**

### 4.3 情绪板

- **应感受**：掌控、清晰、有项目节奏、交付可追踪  
- **不应感受**：被 AI 架空、排程与执行对不上、满屏 planned

## 5. 定位与竞品区隔

| 像 | 不像 |
|----|------|
| 带 AI 角色的个人项目工作台 | 单会话 Copilot |
| 角色有交付契约与规范 | 工作流里只有 prompt 文本框 |
| 人确认后再交接 | 链式 Auto-run 无审核 |
| 有文档/资料库的项目容器 | 仅节点编辑器 |

**主卖点（已决 · 选项 D）**：

> **在项目里配置可交接、可确认的 AI 角色；工作流定义协作，项目主脑与人对齐排程，Dashboard 一眼看清阶段与交付。**

## 8. 语言规范

### 8.1 术语（建议默认）

| 概念 | 对外用语 |
|------|----------|
| 执行单元 | **角色**（主术语）；「智能体」可作括注 |
| 内置协调者 | **项目主脑**（或项目主控，全站统一其一） |
| 引擎 | **工作流** |
| 视图 | **排程** / **Dashboard** |
| 把关 | **确认**（不用「审批流」除非团队版） |

### 8.2 用词

| 推荐 | 避免 |
|------|------|
| 确认、交付物、命名规范、交接 | 100% 自动、无人值守 |
| 项目主脑、排程草案 | AI 替你做主 |
| 最近交付、下一步、预计 | 虚假精确 KPI |

- 首页 / 营销站：「查看产品演示」「预约演示」

## 11. 对外问答口径

| 问题 | 建议回答 |
|------|----------|
| 和 Notion/飞书项目有何不同？ | 我们有**可执行的 AI 角色与工作流**，Dashboard 看交付；排程来自**项目主脑**与你对齐，不是纯手动甘特图。 |
| 排程改会自动跑吗？ | 排程主要是**给人看的共识**；真正执行靠**工作流**。排程更新需通过主脑产出并**经你确认**。 |
| 会不会 AI 乱交差？ | **交付都要经你确认**后才算数并交给下一角色。 |
| 团队版？ | 当前面向**个人项目**；团队协作在路线图中。 |
